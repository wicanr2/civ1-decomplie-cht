# byte-pattern scan 找到 gr_pic.c 家族

之前 ghidra_extract_loadgifpicture.py 失敗 (Ghidra auto-analysis
沒建立 data references)。改寫 ghidra_byte_pattern_scan.py 找
PUSH imm16 指令、imm16 對應 assert string offset。一輪找到 5 個:

  GR_PicRead          @ 10b8:079d (779B)
  GR_PortDataToBitmap @ 10b8:0e36 (902B)
  LoadGifPicture      @ 10b8:11bc (717B)   <- LZW caller
  InvertBitmap        @ 10b8:1489 (259B)
  PicDecompress       @ 10b8:158c (1474B)  <- LZW decoder

全在 code segment 10b8 連續, 符合「一個 .c 檔一個 segment」的
Borland C 16-bit 慣例。Decompile 在 team-a/dumps/03a_*.c。

# LZW 其實沒變體 — 標準 GIF89a

LoadGifPicture 拿 CvPc byte at offset 4 直接傳給 PicDecompress
作 min_code_size。PicDecompress 線 118 顯示
CLEAR = 2 << (param & 0x1f) 看起來像 byte+1 變體, 但實際是
Ghidra 對 cdecl16far stack frame 解讀偏移誤導 (該 param 對應
不是 byte4 而是 y-offset)。

正確: 標準 GIF89a Appendix F:
  offset 0-1: width (BE16)
  offset 2-3: height (BE16)
  offset 4:   min_code_size (直接, 例 7 -> CLEAR=128)
  offset 5:   palette_count - 1
  offset 6+:  palette RGB triples
  剩餘:       GIF89a sub-block 串流 (length-prefixed) +
              LSB-first LZW (CLEAR = 1 << min_code, END = CLEAR + 1)

之前撞牆是初版 decoder 把 byte4 當 mode byte 而非
min_code_size。
